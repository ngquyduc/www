## Context

dConstruct builds a surveillance system on LiDAR. Each sensor streams a point cloud to a server, and operators watch it as a live 3D view in a web app, or play back what was recorded. Over Wi-Fi the live view ran about 2 seconds behind the sensor.

<DconstructFlow />

It is a small startup, so there were no separate teams. I worked on the web app, the part operators actually touch, and on the server side behind it: detecting and tracking people, sensor calibration and some of the C++ endpoints. Before the rebuild, training a new operator took two days.

## What I built

**The operator web app in SolidJS and TailwindCSS**, responsive across the screens operators actually use, on top of the backend's endpoints for connecting sensors, the live view and playback. After the rebuild, training a new operator takes one day instead of two.

**Detecting and tracking people.** In every frame the server finds the people in the point cloud and gives each one a position on the site map. A tracker then follows each person from frame to frame under one ID, and only trusts a track once it has been seen for a few frames, so a stray cluster of points does not count as a person. Those tracks are what the zone counts are built on: how many people walked through an area, and how long they stayed.

**Some of the C++ endpoints behind the app**, the server side the web app calls to connect sensors and fetch live and recorded data.

**Sensor calibration.** Each LiDAR measures in its own coordinates, so the system stores every sensor's position and rotation on the site map in SQLite and uses it to place each point it sees on the map. I worked on getting those values right, so that what a sensor saw lined up with the map.

**A C++ PDF report generator** packaged as a library, so reports come out the same way every time. One project uses it so far.

## Decisions

<Callout kind="Decision" title="Organise the app around what operators do, not how the system is built">
  The fastest way to cut training time was to stop making operators learn the system's structure. The app is laid out around their jobs: connect a sensor, watch live, review a recording. The trade-off is that the screens no longer mirror the backend one to one, so the frontend does more of the work of joining things up.
</Callout>

## In hindsight

I worked on several pieces of the pipeline, from detection and tracking to the app, but never timed one frame all the way from sensor to screen. The 2-second delay operators lived with was decided somewhere along that path, and the UI could only work around it. Next time I'd trace the whole path early on, even through code I don't own.
