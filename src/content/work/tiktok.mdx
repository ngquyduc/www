## Context

Direct messages in TikTok run on an in-house instant-messaging SDK that handles sending and receiving, sync, local storage, unread counts and the public APIs the chat screens are built on. TikTok Shop and Lemon8 build on the same SDK. I work on its iOS side in Objective-C and Swift, as an iOS software engineer on the instant messaging team since July 2025.

Messaging looks simple from the outside: you type, it arrives. Underneath, a phone drops between networks, a real-time connection's credentials expire, pushes arrive out of order, and people switch accounts. Most of my work is making those cases invisible to the person sending the message, and making the SDK easier for other teams to build on.

## What I built

**Automatic resend for failed sends.** When a message fails because of a client-side network error, the client retries it without the user having to tap anything. Failed sends fell by 75%.

**A fallback when the real-time connection's credentials expire**, so a send that would have failed goes through another path. Failures of that kind fell by 24%.

**A reorder buffer for out-of-order pushes.** Real-time messages that arrive out of sequence wait briefly and are put back in order, instead of each gap triggering a fresh fetch from the server. Processing failures fell by 78%, re-fetches halved, and the server team could ship a concurrency change that this had been blocking.

**A fix for data showing up under the wrong account after switching accounts.** Every message payload is now checked against the signed-in user, with tracking to detect a session bound to the wrong account and a tool that reproduces the timing that caused it.

**A cleaner public API for the SDK.** I consolidated about 40 scattered conversation APIs into one protocol-oriented entry point, made the query API type-safe, and removed most of a legacy wrapper layer. Each step shipped behind an A/B test.

**Performance work on change notifications.** I profiled how the SDK tells the UI that conversations and messages changed, using Instruments and signposts, and designed a filtered event system so screens only hear about the changes they care about.

**AI-agent testing for iOS.** Agents drive the app on a Mac or a cloud phone to check a merge request end to end, with screenshots and video. I shared the workflow with the team as reusable skills and guides.

Around this: tech reviews, design docs, on-call for the SDK, and running standups and sprint planning.

## Decisions

<Callout kind="Decision" title="Retry only what the client knows never arrived">
  Automatic resend covers client-side network errors and nothing else. If the server rejected a message, sending it again would at best fail again and at worst post it twice, so those still surface to the user. Narrowing the scope kept the change safe to ship and easy to reason about.
</Callout>

<Callout kind="Decision" title="Wait a moment before fetching">
  When a real-time push arrives with a gap before it, the old behaviour was to fetch from the server straight away. The buffer waits a short time for the missing message first, because most gaps fill themselves. The trade-off is a few milliseconds of added latency in the worst case, in exchange for far fewer failures and server round trips.
</Callout>

## In hindsight

The changes that went smoothly were the ones where the failure already showed up in data before I touched any code, and where the change shipped behind an experiment. For the next reliability problem I'd start by making it measurable, and I'd split large API changes into phases from the beginning rather than discovering the phases along the way.
