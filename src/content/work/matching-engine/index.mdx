## Problem

Many clients send buy, sell and cancel orders at the same time, for many instruments. The engine has to match each order against the best opposite price first, and the earliest order at that price, without a crossed book, a lost fill, or a data race. The assignment was to do that concurrently, so orders for different instruments never wait on each other.

## Architecture

<Arch />

Each client connection gets its own thread. An order first looks up its instrument's book in a shared map, takes that book's lock, and only then releases the map's lock, so two threads working on different instruments run in parallel. Each book keeps its buy and sell orders in two priority queues ordered by price, then timestamp. A second map, from order id to instrument and side, lets a cancel find the right book.

We checked the locking with ThreadSanitizer and the memory handling with AddressSanitizer, and generated test cases with a Python script, from one client up to 40 clients across 10 instruments and 100,000 transactions.
