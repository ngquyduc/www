## Problem

Many clients send buy, sell and cancel orders at the same time, for many instruments. The engine has to match each order against the best opposite price first, and the earliest order at that price, without a crossed book, a lost fill, or a data race. The assignment was to do that concurrently, so orders for different instruments never wait on each other.

## Architecture

<Arch />

In C++, each client connection gets its own thread. An order first looks up its instrument's book in a shared map, takes that book's lock, and only then releases the map's lock, so two threads working on different instruments run in parallel. Each book keeps its buy and sell orders in two priority queues ordered by price, then timestamp. A second map, from order id to instrument and side, lets a cancel find the right book.

The Go version takes the opposite approach: no goroutine shares data. One goroutine per client sends orders to a distributor, which forwards each one to a master goroutine for its instrument; the master hands orders to a buyer and a seller worker over channels, and each worker owns its own queue. A client waits for a done signal before its next order, so orders from one client stay in sequence.

In C++ we checked the locking with ThreadSanitizer and the memory handling with AddressSanitizer, and generated test cases with a Python script: from one client up to 40 clients across up to 10 instruments, plus separate runs of 100,000 transactions with 10 and 20 clients. In Go we compiled with the race detector and ran the same kind of generated tests with 1 to 40 clients.
